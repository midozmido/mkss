# الرفع على cPanel

هذا الدليل مكتوب لاستضافة cPanel تحديدًا، ويبدأ بالسؤال الذي يقرّر كل شيء.

---

## ٠. قبل أي شيء: هل استضافتك تصلح أصلًا؟

النظام يحتاج **Node.js نسخة 22.5 أو أحدث**. ليس تفضيلًا: قاعدة البيانات
كلها مبنية على `node:sqlite` وهي وحدة **مدمجة في Node نفسه** منذ 22.5،
ولا تُنصَّب بـ npm ولا بديل لها. على Node 20 لن يقلع النظام إطلاقًا.

**افحص قبل أن ترفع شيئًا:**

1. cPanel → **Setup Node.js App** → **Create Application** → افتح قائمة
   **Node.js version** وانظر أعلى رقم فيها.
2. إن كان أقلّ من 22.5 فالاستضافة لا تصلح لهذا النظام كما هو. خياراتك:
   - اطلب من الدعم تفعيل نسخة أحدث (كثير من مزوّدي CloudLinux يضيفونها عند الطلب).
   - أو انقل النظام إلى VPS — وهو الأنسب أصلًا لسبب ثانٍ تجده في القسم ٦.

وبعد الرفع، شغّل الفاحص المرفق من **Terminal** في cPanel:

```bash
cd ~/mkss && node doctor.cjs
```

يخبرك في ثوانٍ: نسخة Node، وهل `node:sqlite` تعمل، وهل الكتابة مسموحة،
وهل WAL مدعوم، وما الذي لم تضبطه من متغيّرات البيئة.

---

## ١. أين تضع الملفات

**خارج `public_html`.** ضعها في `/home/USER/mkss`.

السبب ليس ترتيبًا: داخل `public_html` يصير `data/mkss.db` ملفًّا قابلًا
للتنزيل بطلب HTTP واحد — كلمات سر عملائك المجزّأة، ومحادثاتهم، وفواتيرهم.
(يوجد `data/.htaccess` يسدّ الباب على Apache كحزام أمان، لكنه لا يغني عن
وضع المجلد في مكانه الصحيح.)

الرفع: اضغط المشروع `zip` وارفعه بـ **File Manager** ثم Extract، أو
اسحبه من Git إن كان Terminal متاحًا:

```bash
cd ~ && git clone -b claude/customer-support-sites-system-qm032c \
  https://github.com/midozmido/mkss.git mkss
```

> **`npm install` لا يُنفَّذ.** المشروع بصفر اعتماديات: `dependencies` فارغة.
> لوحة cPanel تعرض زرّ **Run NPM Install** — لا تحتاجه، وضغطه غير ضارّ.

## ٢. إنشاء التطبيق

cPanel → **Setup Node.js App** → **Create Application**:

| الحقل | القيمة |
|---|---|
| Node.js version | أحدث نسخة ≥ 22.5 |
| Application mode | Production |
| Application root | `mkss` |
| Application URL | نطاقك أو نطاق فرعي (مثلًا `support.example.com`) |
| **Application startup file** | **`app.js`** |

**`app.js` لا `server.js`.** cPanel تشغّل Node خلف Phusion Passenger، وهو
يستورد ملف الإقلاع من محمّله ولا يشغّله كأمر طرفية. و`server.js` مكتوب
ليعمل بالطريقتين، لكن `app.js` هو المدخل المخصّص لهذه الحالة: يُقلع بلا
شرط، ويُطفئ المراقب داخل العملية (اقرأ القسم ٤ لتعرف لماذا).

## ٣. متغيّرات البيئة

في الشاشة نفسها، قسم **Environment variables**:

| المتغيّر | القيمة | لماذا |
|---|---|---|
| `BASE_URL` | `https://support.example.com` | يُبنى منه كل رابط، ومنه يعرف النظام أن الاتصال مشفّر فيضع علامة `Secure` على كوكي الجلسة. بلا `https` هنا تُرسل الجلسة بلا حماية. |
| `TRUST_PROXY` | `1` | Apache أمام التطبيق. بدونه يُسجَّل عنوان الخادم مكان عنوان الزائر، فينهار حدّ محاولات الدخول: كل العالم يبدو زائرًا واحدًا. |
| `NODE_ENV` | `production` | يفعّل تخزين الملفات الساكنة. |
| `MKSS_SECRET` | ‏64 حرفًا عشوائيًّا | اختياري: بدونه يولّده النظام ويخزّنه في قاعدته. اضبطه يدويًّا إن أردت أن تبقى الجلسات صالحة بعد استعادة نسخة احتياطية قديمة. |
| `MKSS_JOURNAL` | `DELETE` | **فقط** إن قال لك `doctor.cjs` إن WAL غير مدعوم. |

ثم **Restart**.

## ٤. المراقبة — كرون لا مؤقّت

هذه أهم نقطة في الملف كله.

Passenger **يوقف التطبيق عند الخمول**. لو كانت المراقبة مؤقّتًا داخل
التطبيق لتوقّفت مع أول فترة هدوء ليلي، وبقي عميلك يرى آخر فحص وكأنه الآن.
عطلٌ في موقعه لا يعرفه أحد — وهو بالضبط ما اشترك من أجله.

لذلك `app.js` يُطفئ المراقب الداخلي، والمراقبة تأتي من **Cron Jobs**:

cPanel → **Cron Jobs** → Add New Cron Job → **Every 5 Minutes**:

```
cd /home/USER/mkss && /home/USER/nodevenv/mkss/22/bin/node cron/check.js >> data/cron.log 2>&1
```

- استبدل `USER` باسم حسابك، و`22` برقم نسخة Node التي اخترتها.
- **مسار Node الصحيح** معروض أعلى شاشة «Setup Node.js App» في سطر
  `source /home/USER/nodevenv/.../bin/activate` — انسخه منه.
- كل تشغيل يأخذ قفلًا فلا يتراكب مع سابقه، ويستنزف كل المواقع المستحقّة
  لا خمسة فقط، وينتهي خلال أربع دقائق كحدّ أقصى.
- راجع `data/cron.log` بعد ربع ساعة: يجب أن ترى سطرًا كل خمس دقائق.

## ٥. التشغيل الأول

من **Terminal** (أو زرّ Run JS Script في اللوحة):

```bash
cd ~/mkss
source /home/USER/nodevenv/mkss/22/bin/activate   # انسخ السطر من اللوحة
node doctor.cjs        # يجب أن ينتهي بـ «الاستضافة جاهزة»
node seed.js           # ينشئ قاعدة البيانات ويطبع بيانات دخول الأدمن
```

`seed.js` يطبع بريد الأدمن وكلمة سره **مرة واحدة**. انسخهما فورًا.

ثم افتح:
- `https://نطاقك/admin/login` — بوابة الإدارة
- `https://نطاقك/login` — بوابة العملاء

## ٦. حدود يجب أن تعرفها قبل أن تبيع هذا لعميل

**١. الاستضافة المشتركة تقتل العمليات الطويلة.** بعض المزوّدين يحدّون زمن
التنفيذ أو عدد العمليات، فتُقطع دورة مراقبة في منتصفها. لا يفسد هذا
البيانات (الفحص الناقص لا يُسجَّل)، لكنه يُنتج «فجوات مراقبة» متكرّرة.

**٢. المراقبة من مكان واحد.** إن توقّفت استضافتك توقّفت المراقبة — ولهذا
بُني سجل الفجوات، فلا نزعم لعميلك تشغيلًا لم نره.

**٣. SQLite على أنظمة ملفات شبكية.** كثير من الاستضافات المشتركة تستعمل
NFS، وأداء SQLite عليه أضعف وقد لا يدعم WAL. الفاحص يخبرك.

**٤. النسخ الاحتياطي مسؤوليتك.** أضف مهمة كرون يومية:

```
0 3 * * * cd /home/USER/mkss && cp data/mkss.db data/backup-$(date +\%F).db && find data -name 'backup-*.db' -mtime +14 -delete
```

(النسخ أثناء التشغيل آمن مع WAL. علامات `\%` مقصودة — كرون يعامل `%` رمزًا خاصًّا.)

**الخلاصة الصادقة:** cPanel تكفي للبدء ولعدد محدود من العملاء. وحين يكبر
العدد، أو تضيق حدود المزوّد، فالانتقال إلى VPS بـ systemd (راجع
`docs/DEPLOY.md`) أهدأ بالًا — والكود نفسه لا يتغيّر.

## ٧. ماذا لو لم يعمل

| العَرَض | السبب الأرجح |
|---|---|
| صفحة بيضاء أو خطأ 503 | ملف الإقلاع ليس `app.js`، أو نسخة Node أقدم من 22.5. افتح `stderr.log` في مجلد التطبيق. |
| `Cannot find module 'node:sqlite'` | نسخة Node قديمة. لا يُصلحها npm. |
| `SQLITE_CANTOPEN` | أذونات `data/`: `chmod 755 data` |
| الدخول يفشل رغم صحّة البيانات | `BASE_URL` بلا `https` بينما الموقع يعمل بـ `https` — الكوكي تُرفض. |
| «محاولات كثيرة» لكل الزوّار | `TRUST_PROXY` غير مضبوط على `1`. |
| حالة المواقع لا تتحدّث | الكرون لم يُضبط، أو مسار Node فيه خاطئ. راجع `data/cron.log`. |
